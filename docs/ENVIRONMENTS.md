## Identity guard

`packages/config/src/environments.ts` checks, before any DB pool or privileged client
is created (db client, `packages/auth` server/middleware, `drizzle.config.ts`, the
CLIs and the integration-test setup):

- `CRM_ENV` is set and is `local`, `staging` or `production` — no default; the old
  `development` value fails with a rename hint.
- **Local**: Supabase URL and `DATABASE_URL` host are loopback; keys carry no hosted
  project ref; a `postgres.<ref>` user is rejected even on 127.0.0.1 (tunnel).
- **Staging / Production**: URL, legacy JWT keys and `DATABASE_URL` (pooler user and
  direct host) must all name exactly that project. Production credentials therefore
  cannot pass as Staging, and vice versa. `sb_` keys are verified online by
  `pnpm crm` against the target API.
- Deployment rules: `next dev` never runs as production; a Vercel Preview/Development
  deployment refuses Production; Vercel Production refuses anything but production;
  nothing deployed may use `local`.

`pnpm crm` builds the child environment from exactly one source; inherited shell
values for guarded keys are dropped, and for Local, hosted-only integration keys
(`RESEND_API_KEY`, PostHog, Supabase access tokens) are dropped too. Next.js
auto-loaded files (`.env`, `.env.local`, `.env.development[.local]`,
`.env.production[.local]`) may not define Supabase variables at all.

The same resolution drives the app (`pnpm crm --local|--staging`), the integration
tests (`… --test`; the test setup refuses anything but `local`/`staging` it was
given) and migration tooling (`pnpm db`, which takes Local from the CLI and Staging
from the verified Staging file — never from a CLI link).

### Manual verification still needed (someone with access)

1. **Vercel → Project → Settings → Environment Variables**: Production has
   `CRM_ENV=production` and Production values; **Preview** and **Development** have
   `CRM_ENV=staging` and Staging values (or none) — never Production's
   `DATABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`. Do this _before_ merging this branch:
   the guard will (deliberately) refuse to start a deployment whose `CRM_ENV` is
   missing, `development`, or inconsistent with `VERCEL_ENV`.
2. **Supabase dashboard → Production project → Integrations → GitHub**: not
   connected, or "Deploy to production" off and Branching disabled. Now that
   `supabase/migrations/` exists, an enabled integration would apply it on push.
   Same check on Staging (a deliberate `pnpm db staging:push` is the only path).
3. **Staging Auth settings**: custom SMTP off or a sandbox (so password resets for
   the remaining real staff account(s) in Staging go nowhere unexpected).
