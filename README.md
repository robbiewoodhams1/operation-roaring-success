# Operation Roaring Success

A Turborepo-powered pnpm monorepo containing two Next.js applications backed by a set of shared packages.

## Structure

```
operation-roaring-success/
├── apps/
│   ├── admin/        — Internal admin dashboard (port 3001)
│   └── platform/     — Main user-facing platform (port 3000)
└── packages/
    ├── algorithms/   — Business logic and target-scoring algorithms
    ├── auth/         — Authentication helpers and session utilities
    ├── config/       — Shared TypeScript configs, ESLint rules, env validation
    ├── db/           — Database client, Drizzle schema, and types (Supabase)
    ├── telephony/    — Telephony integration (calls, SMS)
    └── ui/           — Shared React UI component library
```

## Prerequisites

- Node.js >= 20.0.0
- pnpm 9.x — `npm install -g pnpm@9`

## Getting Started

Prerequisites for local development: **Docker Desktop** (WSL 2 backend on Windows) —
see `docs/LOCAL_DEVELOPMENT.md`. The Supabase CLI comes with `pnpm install`.

```bash
pnpm install

# Start local Supabase in Docker, build it from supabase/migrations + seed.sql,
# and run the platform against it on http://localhost:3000
pnpm db:reset
pnpm crm --local
```

Sign in with a synthetic account, e.g. `admin@synthetic.invalid` / `local-dev-only`.

## Environments

Three isolated environments, one direction: **LOCAL → STAGING → PRODUCTION**
(`docs/ENVIRONMENTS.md`). Every process declares which one it is via `CRM_ENV`, and
both the CLIs and the app (`packages/config/src/environments.ts`) refuse to run unless
the Supabase URL, API keys and `DATABASE_URL` all belong to it. There is no default.

| `CRM_ENV`    | Target                        | Credentials live in                                  |
| ------------ | ----------------------------- | ---------------------------------------------------- |
| `local`      | Supabase CLI stack in Docker  | generated by the CLI, injected by `pnpm crm --local` |
| `staging`    | hosted `gqkugpjmguufavbladxt` | `apps/platform/.env.staging.local` (git-ignored)     |
| `production` | hosted `wvdwwmfzwvrniwpmiahu` | Vercel → Production env vars (never downloaded)      |

| Command                                | What it does                                                                                           |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `pnpm crm --local` (`--dev`)           | Starts local Supabase if needed, verifies it is loopback-only, runs the platform on :3000 against it   |
| `pnpm crm --staging`                   | Verifies the Staging file offline and online, then runs the platform on :3000 against Staging          |
| `pnpm crm --local --test`              | Database integration tests against Local (`--staging --test` for Staging; every test rolls back)       |
| `pnpm crm --prod --credentials <file>` | Production `next build` + validation. Never opens a DB session, starts a server, migrates or deploys   |
| `pnpm crm --status`                    | State of all three environments, blocking `.env` files, CLI link and MCP servers. Never prints secrets |

Database changes follow one migration history in `supabase/migrations/` —
`pnpm db --help`, `docs/MIGRATIONS.md`. Production database changes follow
`docs/RELEASE.md` and are never made from development tooling.

Rules the CLI enforces:

- `apps/platform/.env`, `.env.local`, `.env.development`, `.env.development.local`,
  `.env.production` and `.env.production.local` must not define Supabase variables —
  Next.js loads them automatically, so they could override the selected environment.
- Guarded variables inherited from your shell are dropped; they come only from the
  selected source. Local runs also drop hosted-only integration keys.
- A local `next dev` server can never run as `production`; a Vercel Preview can
  never use Production; nothing deployed can use `local`.
- `pnpm crm --prod` prerenders `/login`, whose layout reads `app.platform_settings`
  (one read-only `SELECT`) — the same thing every Vercel build does.

Deploying to production is a separate, explicitly approved operation (Vercel).
Vercel's Production environment must define `CRM_ENV=production`; Preview must use
`CRM_ENV=staging` with Staging values.

Apps run on:

- Platform: http://localhost:3000
- Admin: http://localhost:3001

## Common Commands

| Command             | Description                                 |
| ------------------- | ------------------------------------------- |
| `pnpm crm --local`  | Run the platform on local Supabase (Docker) |
| `pnpm crm --status` | Show environment configuration              |
| `pnpm db:reset`     | Rebuild the local DB (migrations + seed)    |
| `pnpm db:verify`    | Docker-free migration replay (as in CI)     |
| `pnpm dev`          | Start all apps in watch mode                |
| `pnpm build`        | Build all packages and apps                 |
| `pnpm lint`         | Run ESLint across the monorepo              |
| `pnpm type-check`   | Run TypeScript type checking                |
| `pnpm format`       | Format all files with Prettier              |
| `pnpm format:check` | Check formatting without writing            |
| `pnpm clean`        | Remove all build artifacts and node_modules |

To target a specific workspace:

```bash
pnpm --filter @roaring/platform dev
pnpm --filter @roaring/admin build
```

## Adding a New Package

1. Create a directory under `packages/` with a `package.json` naming it `@roaring/<name>`
2. Extend `@roaring/config/tsconfig/package` in its `tsconfig.json`
3. Add it as a dependency to whichever apps or packages need it
4. Turborepo picks it up automatically — no root config changes required
